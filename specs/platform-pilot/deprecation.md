## 退役类型

- **类型**：advisory
- **理由**：**compulsory 在本形态下技术上不可实现**（见下）。平台仍可用、无安全或合规驱动；
  退役动机将是"方法论演进到下一代"或"维护者停止投入"，而非"必须停用"
- **替代方案**：无同类替代品。使用者可**永久保留已 `e2e init` 的项目文件**继续用
  （它们已属其仓库，且代码 Apache-2.0 允许自由使用与分发）
- **owner 与资金**：yongqian 负责推动到底；本形态退役无基础设施成本，投入 = 文档维护工时
- **compulsory 专属**（advisory 填"不适用"）：
  - 迁移工具：不适用
  - 强制截止日：不适用

**为什么 compulsory 不可能**：平台有三个交付面，**没有一个可以强制回收**：

| 交付面 | 为什么收不回 |
|---|---|
| **已 `e2e init` 进使用者项目的文件** | 那些文件**已属对方仓库**。我方无权也无技术手段触碰（门禁④ 演练 D 实测：仓库侧 revert 后对方文件 sha 不变） |
| **已 clone 的副本** | 同上，且 Apache-2.0 明确授予了永久使用权 |
| **已装的插件缓存** | 实测：`claude plugin uninstall` 后**可执行缓存仍在盘上**（`.orphaned_at` 标记，9 个 .sh） |

硬把它写成 compulsory 等于承诺一件做不到的事。

## 本次演练暴露的形态级难点（写进手册）

1. **平台形态的退役比产品形态更难收回**。demo 产品只有"已下载的副本"一个不可逆点；
   平台有**三个**：已 init 进对方仓库的文件、已 clone 的副本、已装插件的可执行缓存。
   其中第一个最硬——那些文件**已经是别人代码库的一部分**了。
2. **无遥测 ⇒ 退役永远缺"已无人使用"的证据**（与 demo 同类，但更严重）：
   服务端系统靠"近 30 天 QPS=0"放行退役；本形态**没有这个数据源，也永远不会有**。
   GitHub traffic API 只有 14 天窗口且需 push 权限，插件安装量无任何接口可查。
   手册必须给出替代判据（观察窗内零 issue、owner 主动决策），
   **而不是让人在模板里填一个编造的数字**。
3. **许可证选择直接决定退役的"善后质量"**。因为代码 Apache-2.0、文档 CC BY-SA 4.0，
   退役后使用者的既有投入**不会作废**，且社区可接手。
   若当初选了限制性许可，退役 = 使用者被困住。**这一点在选许可时就该想清楚。**
4. **通知只能是被动的**，且盲区比 demo 更大：已 `e2e init` 的人**不会回访仓库**——
   他们拿到的是文件，不是订阅。
