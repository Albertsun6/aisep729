## 假设陈述

For **平台作者本人与后续每个 adopt 本平台的仓**, who **依赖本仓探针作为唯一真实防线、但其中数个探针已被 mutation 实测证实假绿或失守**, the **platform-hardening 修复批次** is a **平台自身的质量硬化交付**, that **把已证实的假绿全部转红、把签字语义最便宜的两处做实、把强制力门槛按异构评审共识提高一档**。

## 最险假设（RAT）

**假设**：这些修复能在不破坏现有 106 条负样本与七阶段串锁语义的前提下落地（尤其 A5/B2' 要动 gate.sh 信任根）。
**最便宜验证**：每条修复先写"对旧实现必红、对新实现必绿"的负样本再动实现；全量套件 + 全部平台探针回归绿；完成后对 diff 做异构评审。

## 不做什么（No-gos）

- CI marker 计数（自证无保障，评审共识删除）；同文件内容摘要（防不了同域篡改）
- 门禁块四行契约改动；测试框架引入；动 platform-pilot 已批台账的历史
- D6 服务端完全闭合（单人仓无 org 级 required workflow——如实写入已知限制，不假装解决）

## FAQ

**Q1：修复完成后能宣称"门禁有强制力"吗？**
不能升格。B1/B6 只是提高漂移门槛，"check 内容由 PR 自控"的结构性限制仍在；随 B1 落地把这条补进手册 §7 与 README 已知限制。

**Q2：为什么不先做超级个体门禁拓扑（评估报告 C1）？**
C1 是方向性重设计（含修宪依赖），已单独立项走门禁⓪；在烂地基上重设计拓扑没有意义，先拔假绿。

**Q3：为什么没有 prd/spec/tasks 全链台账？**
本 feature 走轻量通道：prfaq + 经异构评审定稿的行动计划（逐条带验证方式与复杂度点）代 tasks。这是 C1 轻量通道的第一个真实用例，偏差在此显式登记——不是静默绕过（评估报告 D13 的教训）。
